# 测试驱动开发

通过短小的红灯、绿灯、重构循环，逐步实现一个已明确的可观察行为。测试定义和保护行为，不能成为对当前内部实现的复述。

## 开始前

从已确认的需求、spec 或缺陷复现中选定一个行为。明确其公共入口、输入、输出、边界条件，以及预期值所依据的独立业务事实。

如果行为、接口或交互仍在探索，不要用 TDD 过早固化猜测。先澄清需求或制作原型。

## 循环

每次只推进一个纵向行为切片：

1. 通过公共接口写一个聚焦的自动化测试。
2. 运行它，并确认它因新行为尚未实现而失败，不是因为测试环境、语法或设置问题。
3. 只写让该测试通过所需的最小实现。
4. 重新运行测试；通过后才考虑重构。重构后运行相关测试，并在交付前运行与改动相称的验证范围。

不要先堆积一批测试再开始实现，也不要先完成实现再补写测试。

## 测试质量约束

- 断言可观察的输入、输出、状态变化或公共契约，不断言私有变量、私有辅助函数或内部调用顺序。
- 期望值必须来自独立的业务规则、固定样例或可信夹具，不能用待测逻辑的镜像计算得出。
- 夹具必须确定且隔离，不依赖测试顺序、真实时钟、未固定的随机值或共享可变状态。
- 测试名称说明业务能力或缺陷场景，而不是实现方式。

如果一个新测试在未修改实现前就通过，立即检查它是否断言了错误行为、覆盖了已有行为，或没有真正触达目标路径。

## 结束

完成已选定的行为切片后，说明测试覆盖的行为和已运行的验证。不要把未确认的后续需求作为顺带实现加入。
